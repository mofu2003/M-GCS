# MgCore FFI API Catalog

Current contract baseline: `0.0.79`. The current audit counts 306 exported
`mg_*` symbols, with 89 used by Flutter and 220 reached by tests; 83 are not yet
consumed by either the Flutter shell or tests. These counts
are generated by `tools/audit_status.sh`; they do not change the stability
rules below.

`ffi_api.h` is the complete public C ABI. Every `char*` result, including an
event callback payload, is owned by the caller and must be released with
`mg_free_string()`.

## Stability Rules

- **Preferred**: available to new frontend and external consumers. Keep the
  JSON envelope and function signature stable within the current major ABI.
- **Compatibility**: exported for existing tools. Do not add new consumers or
  new behavior to these names. A replacement is listed where one exists.
- **Specialized**: public, but intended for a feature-specific client rather
  than a general-purpose client. Its lack of a first-party binding does not
  make it removable.

No compatibility symbol may be removed until a documented ABI-major release
and a migration note have been published.

Parameter full-list downloads expose their state through
`mg_operations_get_snapshot().params`. `mg_operations_cancel("params")` aborts
the active list/recovery transaction, keeps a `cancelled` terminal state with a
reason, and can be followed by a fresh `mg_params_request_all` call.

The same snapshot shape is used for `mission`, `calibration`, and `log`
operations. Calibration cancellation reuses the existing MAVLink cancel command
path and preserves the calibration service's `cancelled` stage. Log download
cancellation sends `LOG_REQUEST_END` and keeps the adapter's terminal status.

Existing first-party bindings deliberately cover connection, dashboard,
parameters, servo/RC telemetry, serial mapping, calibration, and the
real-time waveform buffer. Mission,
flight command, geofence, payload, logging, SITL, and firmware APIs are
specialized public surfaces that are not yet wired into every client workflow.

`mg_waveform_poll` is the one entry point that writes into caller-owned memory
instead of returning JSON: flight-controller waveforms are large and would
otherwise be re-parsed on every UI frame. The caller allocates
`out_max_points * 10` floats and receives the number of points written, with
`window_ms` selecting how much history to return (`<= 0` means the whole
buffer) and `instance` selecting which IMU's buffer to read (0 is IMU1).
Point layout is
`[relative_ms, accel_x, accel_y, accel_z, gyro_x, gyro_y, gyro_z, mag_x, mag_y, mag_z]`;
all nine axes of one point come from the same IMU sample, so the client never
has to time-align them. When the selected
window holds more frames than `target_points`, values are decimated with a
per-bucket min/max envelope so spikes survive, and the buckets are aligned to
an absolute time grid so an existing point never moves sideways when new data
arrives. Accelerometer is m/s², gyro rates are degrees per second, and
magnetometer is gauss.
`mg_waveform_get_instances` reports which instances the link is actually
carrying, so a client can build one selector per detected IMU and compass:
`{"imu":[{"index","active","age_ms","name"}],"mag":[…]}`. Detection follows
received data rather than firmware parameters — `SCALED_IMU`, `SCALED_IMU2`
and `SCALED_IMU3` are the three per-instance messages, and an instance counts
as a magnetometer source once it reports a non-zero field vector. Index 0 is
always listed so the client has a default before any data arrives.
`mg_waveform_clear` drops the buffered history (also done automatically when a
session connects or disconnects).

## Mission Planning Document

The mission planning document is the preferred offline editing model. It is
separate from the compiled MAVLink `MissionPlan`: editing, validation, undo,
redo, save, and load never write to the vehicle.

Lifecycle:

```text
mg_mission_doc_create/get
    -> mg_mission_doc_apply (local revision-checked edits)
    -> mg_mission_doc_validate
    -> mg_mission_doc_compile
    -> mg_mission_doc_upload (explicit write)
    -> mg_mission_doc_verify (compare vehicle readback)
```

`mg_mission_doc_apply` accepts one operation per call. Supported operations
are `add`, `update`, `remove`, `move`, `clear`, and `replace`. Except for
`replace`, mutation operations use `entity` or `entity_id` and may include
`expected_revision`; a stale revision is rejected.

The document JSON schema is versioned by `schema_version`. The source
document contains:

- `metadata`: id, name, description, firmware profile, vehicle type.
- `home`: optional home latitude, longitude, and altitude.
- `defaults`: frame, altitude, and speed used when an entity omits them.
- `revision`: monotonically increasing local revision.
- `entities`: ordered mission entities with a stable `id`, command, frame,
  coordinates, altitude, four command parameters, and enabled state.

`mg_mission_doc_export` returns the versioned task document JSON.
`mg_mission_doc_save/load` do not enforce a filename extension; use `.mission.json`
for new files.
`mg_mission_doc_import` loads that JSON without uploading to a vehicle.
`mg_mission_doc_save/load` provide the same operation through a filesystem
path.

`mg_mission_doc_compile` returns `valid`, the compiled `MissionPlan`, a
source-entity-id list, and structured diagnostics. `mg_mission_doc_upload`
requires the expected document revision, compiles locally, rejects validation
errors, and then starts the existing mission transfer. ArduPilot home-item
injection remains in the existing transport adapter.

`mg_mission_doc_verify` compares the compiled document with the current
vehicle mission after a completed full download. Equivalent MAVLink `_INT`
coordinate frames are normalized before comparison. Calling verify after upload
but before download returns `invalid_state`. It returns `matches` plus structured
differences with `index`, `field`, `expected`, and `actual` for item count, command,
frame, meaningful position/altitude fields, declared parameters (including the
`NaN`/zero unset normalization), `autocontinue`, `mission_type`, and ArduPilot Home.
Accepted protocol normalizations are returned separately as `normalizations` with a
`reason` and do not make `matches` false.

`mg_mission_doc_import_from_vehicle` replaces the document's entities with the
vehicle's current mission. It matches Mission Planner's *Read* and QGroundControl's
*Download*: it requires a completed download (`invalid_state` otherwise), and the
caller is responsible for confirming before local edits are overwritten. Imported
items keep command, frame, parameters and position; parameterized survey intent
cannot be recovered from the compiled mission. `_INT` coordinate frames (5/6/11)
are normalised to 0/3/10 on import, because the document stores positions as
degrees and compiles back to degE7 itself. `MAV_FRAME_MISSION` (2) is not a
geographic frame: its `x/y` are `param5/param6`. Non-location commands therefore
do not become fake waypoints, while position-bearing commands such as fixed-wing
`NAV_TAKEOFF` retain their coordinates.

Geofence is a separate MAVLink mission type (`MAV_MISSION_TYPE_FENCE`), so it is
not part of the mission upload. `mg_mission_doc_compile_fence` compiles the
document's `geo_fence` into fence mission items without touching the vehicle and
returns `item_count` plus the compiled plan. `mg_mission_doc_upload_fence`
requires the expected document revision and starts a fence transfer;
`mg_mission_doc_clear_fence` clears the vehicle fence. The encoding matches QGC
`GeoFenceManager`: polygons use
`MAV_CMD_NAV_FENCE_POLYGON_VERTEX_INCLUSION/_EXCLUSION` (5001/5002) with `param1`
set to the vertex count, circles use
`MAV_CMD_NAV_FENCE_CIRCLE_INCLUSION/_EXCLUSION` (5003/5004) with `param1` as the
radius, and the breach-return point uses `MAV_CMD_NAV_FENCE_RETURN_POINT` (5000)
in `MAV_FRAME_GLOBAL_RELATIVE_ALT`. Fence upload/clear, like mission upload, are
start-only and map onto the existing fence transfer progress.

Rally points are also a separate MAVLink mission type (`MAV_MISSION_TYPE_RALLY`).
`mg_mission_doc_compile_rally` compiles the document's `rally_points` without
touching the vehicle; `mg_mission_doc_upload_rally` (with the expected document
revision) starts a rally transfer and `mg_mission_doc_clear_rally` clears the
vehicle rally points. The encoding matches QGC `RallyPointManager`: one
`MAV_CMD_NAV_RALLY_POINT` (5100) per point in
`MAV_FRAME_GLOBAL_RELATIVE_ALT`, with `param5/6/7` as latitude/longitude/altitude.

`mg_mission_doc_import_fence_from_vehicle` and
`mg_mission_doc_import_rally_from_vehicle` read the vehicle fence/rally sections
back into the document. They follow `mg_mission_doc_import_from_vehicle`: they
require a completed download of that mission type (`invalid_state` otherwise)
and the caller decides whether to overwrite local data. The inverses are
`geo_fence_from_plan` / `rally_points_from_plan` in Core, whose fence grouping
matches QGC `GeoFenceManager` (consecutive vertices with equal `param1` belong to
one polygon; a changed vertex count or inclusion flag mid-polygon is rejected).

Fence and rally transfers report progress through
`mg_operations_get_snapshot().fence` / `.rally` using the same field names as
`.mission` (`type` is `fence_transfer` / `rally_transfer`). Frontends should poll
that section instead of assuming only the mission transfer is observable.

`mg_mission_doc_verify_fence` / `mg_mission_doc_verify_rally` mirror
`mg_mission_doc_verify` for the two separate mission types. After a completed
download they compare the document against the vehicle and return `matches`,
`difference_count` and a `differences` array whose entries carry `index`,
`field`, `expected` and `actual`. Comparison honours the tolerance argument and
covers polygon/circle geometry, breach-return, and rally coordinates with altitude.
Dynamic ArduPilot Home changes are returned separately through
`home_sync_count` / `home_sync` and do not affect mission-item matching.

Upload is start-only, for both `mg_mission_doc_upload` and the compatibility
entry `mg_mission_upload`: a successful return means the transfer was started,
not that the flight controller finished receiving it. `mg_mission_doc_upload`
reports `state: "uploading"` for that reason. Poll `mg_operations_get_snapshot`
(or `mg_mission_get_progress`) until it reports completion. Verification also
requires a completed full download, so the safe sequence is upload -> poll ->
download -> poll -> `mg_mission_doc_verify`. Treating the upload return value
as completion is a bug.

`mg_operations_cancel("mission")`, `("fence")` and `("rally")` abort the
active transfer of the corresponding mission type. The
backend resets the transfer state, marks it with
`MAV_MISSION_OPERATION_CANCELLED`, and sends a matching `MISSION_ACK` to the
vehicle. It returns `canceled:false` when no mission transfer is active; a
completed or failed transfer is not retroactively cancelled.

Mission operation snapshots include both `result` and QGC-style `result_text`.
The text mapping follows QGC `PlanManager::_missionResultToString`, so a
rejected mission reports unsupported frame/command, invalid parameters, no
space, denied, or cancellation instead of only a numeric MAV_MISSION_RESULT.

`mg_mission_get_command_catalog` exposes command names, a Chinese `label`, the
document `entity_type` for each command, categories, whether a
position or altitude is required, and per-parameter MAVLink index, labels,
units, types, defaults, ranges, required flags, and enum options. Parameter
`index` maps directly to `params[index - 1]`. Frontends should render command
forms from this catalog rather than hard-coding MAV_CMD parameter semantics.

`mg_mission_doc_export_format` / `mg_mission_doc_import_format` accept
`"waypoints"` and `"plan"`. The `.plan` implementation maps QGC `SimpleItem`
entries and supports both current seven-value `params` items and legacy
`coordinate` arrays. QGC `ComplexItem` (Survey, CorridorScan, ...), GeoFence and
Rally sections are preserved as formal `MissionComplexItem` /
`MissionGeoFence` / `MissionRallyPoint` document models and rebuilt on export;
complex items remember their position via `entity_insert_index` and are
interleaved with simple items in the original order. ComplexItem inner fields
are read-only for now. QGC saves its computed mission items inside the complex item
(`TransectStyleComplexItem.Items`), so M-GCS expands those items in place instead of
re-deriving survey geometry; an item without that section still fails validation
(`complex_item.unsupported`) so it cannot be compiled or uploaded. Expandable items
compile and upload normally and produce a `complex_item.expanded` warning. Disabled entities,
parameterized survey entities and unrepresentable altitude fields fail or
return entries in the `warnings` array. Import/export responses include
`warnings` even when empty.

`survey_grid` and `corridor` entities are parameterized: the document stores the
intent (`survey.width_m`, `survey.length_m`, `survey.angle_deg`,
`survey.cross_grid`, `survey.end_lat` / `survey.end_lon`,
`survey.corridor_width_m`, camera and overlap fields) and `mg_mission_doc_compile`
expands them into waypoints through the existing `SurveyCalculator`. Every
expanded item maps back to the same source entity in `source_entity_ids`, so a
client renders one row per survey block rather than one per generated waypoint.
See `docs/MISSION_PLANNING.md` for the full example.

### Deprecation policy

Compatibility entries stay exported so existing binaries keep linking; they are
frozen rather than removed. Concretely:

- No new behavior is added to a compatibility name. Bug fixes that make a
  compatibility entry stop reporting false success are allowed, and are called
  out in the `CHANGELOG.md` entry of the release that ships them.
- New consumers must use the replacement listed above.
- Removal happens only at an ABI-major release with a migration note. Until
  then, `MGCORE_API` keeps the plain C signature; no compiler `deprecated`
  attribute is applied, because that would emit warnings in consumers that are
  already pinned to the old name.

`mg_connection_open` accepts one explicit URI (`serial://`, `tcp://`, or
`udp://`) and returns a physical link ID without changing active/UI focus.
Use `mg_connection_list` to read the link → route → vehicle mapping,
`mg_connection_get_session_state` / `mg_connection_close` with the link ID to
inspect or close the physical link, and `mg_connection_close_route` to remove
one vehicle route from a shared link. These operations do not depend on
selection.

`mg_vehicle_set_signing_key` 接受 64 个十六进制字符的 32 字节密钥。signing 状态、link ID、timestamp 和 stream 表都归属具体 `MavlinkAdapter`；设置/清除会遍历该 Vehicle 的全部 route。`mg_vehicle_set_signing_candidates` 接受 `[{name,key_hex,timestamp_ticks}]`，收到已签名包时在核心层逐一验证 MAVLink2 HMAC，命中后自动启用并将密钥同步到全部 route。`mg_vehicle_get_signing_status` 返回 `enabled`、`status`、`status_code`、`key_name`、`auto_detected`、`candidate_count` 和 `timestamp_ticks`，状态包括 `ok`、`bad_signature`、`old_timestamp`、`replay` 等。`mg_vehicle_send_setup_signing` 发送未签名的 SETUP_SIGNING 消息，用于把密钥和初始时间戳交给飞控。

`mg_vehicle_get_session_status` reads GPS fix/satellite count, WGS-84
position/altitude, heading, battery voltage/remaining percentage, and link
heartbeat for one session without changing active/UI focus. Position fields
are `position_valid`, `lat_deg`, `lon_deg`, `alt_msl_m`, and `alt_rel_m`. Telemetry fields are nullable when the backend cache
has no fresh sample; clients should display unavailable values instead of
reusing stale readings.

`mg_vehicle_open` and `mg_vehicle_close` are vehicle-level compatibility
wrappers; `mg_vehicle_open` additionally accepts a bare serial device path and
`mg_vehicle_close` removes the vehicle and all of its routes.
`mg_connection_connect`, `mg_connection_disconnect`, and TCP/UDP convenience
helpers remain legacy single-active-session wrappers. The connect wrappers
select the session they create so existing active-vehicle commands continue to
work. New code should use the session-oriented `mg_connection_*` lifecycle.

### MV1 framework consumer

Flutter's `fleet/FleetFfiBackend` consumes the existing session lifecycle,
`mg_vehicle_list`, and `mg_vehicle_get_active` without new exports or schema
changes. List/status reads do not select vehicles. `mg_vehicle_list` holds a
shared lifetime snapshot while serializing entries to survive registry removal.
This does not yet provide shared-link multi-system discovery, component-scoped
telemetry or explicit vehicle-target flight commands. See
[the implementation plan](../../docs/planning/MULTI_VEHICLE.md).

### Targeted flight command routing

`mg_command_execute_for_vehicle()` is the preferred multi-vehicle command entry.
It resolves one specific vehicle/session, installs a thread-local target
override for existing command implementations, and restores the previous
override before returning. It does not call `mg_vehicle_select()`, so concurrent
UI focus polling never observes a temporary target switch. Existing
`mg_command_*` symbols remain the compatibility surface for single-vehicle
callers.

The JSON payload contains `command` and optional `args`; see
`ffi_api_flight.h` for the accepted command names. A missing target returns
`MG_ERROR_NOT_FOUND`; malformed or unsupported command JSON returns
`MG_ERROR_INVALID_PARAM`.

## Adding or Retiring APIs

1. First reuse an existing preferred API or extend an aggregate snapshot.
2. Add the declaration to the matching `ffi_api_*.h`, implementation tests,
   and a catalog entry.
3. Preserve JSON envelope and ownership rules.
4. Mark replacements as compatibility before removal; do not delete symbols
   based only on current first-party usage.
| Session mission | `mg_vehicle_get_session_mission(core, vehicle_id)`；读取该 Vehicle 缓存的普通任务条目，返回 `valid`、`revision`、`current_index` 和 `items[{seq,command,frame,lat_deg,lon_deg,alt_m,current}]`；仅包含 mission_type=0 且可解释为 WGS-84 的 frame（0/3/5/6），不等价于完整任务文档；返回字符串由 `mg_free_string()` 释放 |
| Async flight command | `mg_command_submit_for_vehicle(core, vehicle_id, command_json)` 返回 ticket；`mg_command_poll(core, ticket)` 非阻塞查询终态。单 Vehicle 同时只允许一个 worker，结果中的 `result.success` 必须由 ACK/状态确认决定；ticket 完成后只能消费一次。 |
