# 仓库协作流程

所有协作者遵循同一套仓库约束。任务范围与操作授权以用户指示为准，模型名称不决定代码所有权或审批权限。

## 任务开始

1. 检查 `git status`，保留已有修改。
2. 按 `AGENTS.md` 读取与任务相关的约束；涉及功能行为时核对 `parity.md` 与本地上游参考。
3. 明确改动范围、验收方式和现有局限。简单任务直接执行，复杂任务先列简短计划。

## 多人或多 agent 并行

- 仅在任务需要且得到相应授权时并行；为各协作者分配独立模块或文件。
- 有提交冲突风险时使用独立 worktree，并标明基准提交。
- 共享 FFI、状态模型或构建设置的改动先对齐契约，避免各层分别修改成不兼容版本。
- 汇总时由负责当前任务的协作者检查最终 diff、解决冲突，并对汇总后的代码运行门禁。
- 其他协作者的报告是线索，不能代替对最终代码和测试的核对。

## 实现与验证

- 本地阅读、编辑和安全测试按用户授权直接执行，不因文件数量或 agent 名称额外审批。
- 修改公开 FFI 时遵守 `docs/constraints/ffi-contract.md`：头文件、实现、合约测试、API 目录与相关文档成套更新。
- `python3 tools/check_ffi_contract.py --write-catalog` 更新接口目录；不删除已有 ABI 导出。
- 开发期间可使用 `tools/preflight.sh --changed`；提交前运行完整 `tools/preflight.sh`。
- 本地验证包括 UI token、Flutter analyze/test、C++ offline/simulation、当前主机可构建的前端包及共享库符号核对。
- 通过本机门禁不代表其他平台已实跑；Windows、Linux、Android 由相应主机或 CI 构建，UI 截图验收另行记录。
- 硬件测试不进入自动门禁，按 `release-and-hardware.md` 的串口独占和现场确认要求执行。

## 交付

- 文档记录当前行为与真实验证结果，不把待决定事项描述为已实现。
- 已关闭偏差从 `known-deviations.md` 移除，并在 CHANGELOG 或提交说明中保留编号。
- 未解决的差异继续登记，写清实际影响与后续工作。
- 最终说明列出修改、验证结果和限制；推送、发布与远端操作按用户明确指示执行。
