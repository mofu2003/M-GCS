## 方向摘要

M-GCS 当前已有任务文档编辑、后端校验/编译、任务上传/下载/验证、`.waypoints` / QGC
`.plan` SimpleItem 互操作、地图 Home/飞机位置和基本引导操作。近期不应继续堆叠零散
页面，而应优先把已有安全敏感工作流做成可靠闭环，再扩展复杂格式和领域覆盖，随后
补足运维诊断与平台实机验证。

目标不是逐项复制 Mission Planner（MP）或 QGroundControl（QGC），而是按模块选择
质量更高的实现：任务模型、链路生命周期、跨平台结构和测试治理优先参考 QGC；
ArduPilot 专用命令、参数、校准、固件和飞行行为优先参考 MP。组合时明确边界，
协议语义、任务编译和校验仍集中在 M-GCS 后端。默认归属见
[MP / QGC 上游实现择优准则](../specs/upstream/SELECTION_STRATEGY.md)。
完整能力差距和建议优先级见 [路线图与功能差距分析](ROADMAP.md)。

## 本轮维护决策

M-GCS 不选择“全盘 MP”或“全盘 QGC”，而采用明确的组合边界：

```text
官方 MAVLink / 飞控协议事实
              ↓
QGC：框架、生命周期、状态机、取消、跨平台和测试治理
              +
MP：ArduPilot 参数、校准、模式、任务字段和现场兼容
              ↓
M-GCS Core -> FFI -> Flutter
```

维护顺序固定为：

1. 先修复安全敏感流程的状态、错误和恢复语义。
2. 再拆分内部大文件，保持公开 FFI 和用户行为不变。
3. 再补任务、参数、围栏/Rally 和平台能力。
4. 最后才扩大 UI 和产品功能范围。

本轮不做框架替换，也不复制 QGC 的 Qt/QML 或 MP 的 WinForms 结构。

## 当前基线与差距

| 领域 | M-GCS 当前基线 | MP / QGC 可借鉴点 | 当前主要差距 |
| --- | --- | --- | --- |
| 任务规划 | 任务文档、命令目录、测绘实体、校验/编译、上传/下载/验证、operations 进度与取消、回读核对、脏状态、拖拽排序；Flutter 地图规划面板 | 两者均采用显式 Read/Write 或 Download/Upload；覆盖本地未保存内容前先确认 | Survey/Corridor 可视编辑、Structure Scan/固定翼着陆、围栏/Rally 地图编辑和地形规划仍未补齐 |
| 地图与飞行操作 | Home/飞机标记、地图偏好保存、引导操作及确认 | QGC 按飞行状态、机型和 capability 控制动作可用性；关键操作前确认 | 继续核对定位有效性、能力差异和异常状态呈现；避免对不支持动作显示可执行入口 |
| 任务格式与相关领域 | `.waypoints` 互操作；QGC `.plan` SimpleItem、ComplexItem、GeoFence、Rally 已纳入文档模型并往返无损；ComplexItem 复用 QGC 已算好的任务项参与编译/上传；围栏和 Rally 几何已校验，并可各自按 QGC 编码编译/上传/清除/回读与 verify | QGC `.plan` 将任务及相关规划信息组织为可保存文件；MP 有成熟 ArduPilot 任务与参数流程 | ComplexItem 内部字段仍只读（几何来自 QGC，不可在 M-GCS 编辑）；围栏/Rally/ComplexItem 统一编辑工作流仍缺 |
| 诊断与长操作 | 有连接/系统/遥测诊断及 operation 后端 API | QGC 将连接、车辆状态、命令结果和进度反馈串成连续工作流；MP 提供面向 ArduPilot 的丰富检查 | Flutter 尚未完整使用聚合诊断和长任务取消/统一进度；不同页面状态体验不一致 |
| 平台质量 | macOS 主开发路径；Windows/Linux 构建路径存在；Android USB Host 基础工程存在 | MP 覆盖 Windows 为主的 ArduPilot 场景；QGC 重点支持桌面和移动平台 | Windows 尚缺系统化真机验收；Linux/Android 串口和关键工作流需明确支持级别并验证 |

## 阶段计划表

阶段不绑定日期，也不自动等同于一个发布版本。优先按表中顺序推进；若用户改变重点，应先重排阶段，再开始涉及 FFI 或安全行为的工作。

| 阶段 | 优先级 / 目标 | 主要工作 | 依赖与风险 | 完成标准 |
| --- | --- | --- | --- | --- |
| A. 任务闭环可靠性 | P0；让现有规划功能可预期、可恢复 | 统一任务上传/下载进度、成功/失败/超时和取消入口；本地文档脏状态及覆盖确认；上传完成后显式回读并展示验证结果；校验错误定位到对应实体/参数；航点与地图双向选中、列表重排 | 先复核现有 `mg_mission_get_progress`、operation API 和页面状态，优先复用；若需改 FFI，必须同步实现、测试、API Catalog、文档和绑定；取消传输需明确协议终止语义 | 离线/模拟测试覆盖成功、拒绝、超时、断链、取消及重试；模拟“本地未保存任务被下载覆盖”必须先确认；回读验证能区分通过与差异；列表重排后地图序号和编译顺序一致 |
| B. 任务文件与领域互操作 | P1；提高任务可交换性，不破坏现有任务契约 | 设计 QGC `.plan` 导入/导出映射；对 unsupported 字段给出诊断而非静默丢弃；评估围栏与 Rally 纳入统一文件/任务文档的边界；补齐几何校验、版本化和往返测试 | 先定义可逆/不可逆字段映射；Survey/Corridor 导出到普通航点会丢失设计意图；Fence/Rally 涉及不同 MAVLink mission type 和飞控支持差异 | 有格式规范与字段映射表；有效样例 round-trip 测试通过；未知字段/不支持命令有明确告警；不会静默改变飞控任务；围栏/Rally 独立类型和能力差异有测试 |
| C. 诊断与运维工作流 | P1；缩短连接、任务、参数和校准问题的定位时间 | Flutter 接入聚合诊断快照；统一长任务进度、取消和终态；连接质量/遥测 freshness 可见；参数变更结果可追踪；校准历史和飞行日志入口按现有后端能力梳理 | 依赖 FFI 生命周期和事件线程安全；诊断字段需有稳定语义；不新增只展示却无可操作价值的卡片 | 模拟断连、超时、拒绝和重连时状态无歧义；页面隐藏时停止轮询；进度与后端状态一致；取消后资源释放且可重新开始 |
| D. 跨平台实机稳定性 | P1；将“有构建路径”推进到“关键流程可验收” | Windows：串口连接/断连、遥测、参数读写、校准、任务上传下载；Linux：原生构建和串口基本流程；Android：先明确支持范围，再验证 USB-serial 权限、设备拔插和生命周期 | 需要对应平台设备、飞控和安全测试条件；飞控串口是排他资源；Android 驱动差异大，不宜承诺通用支持前提 | 每个平台有版本化验收清单、驱动/设备记录和结果；无硬件的场景由 simulation 覆盖；明确标注已验证、未验证和不支持项 |
| MV. 多机连接与焦点管理 | P1；当前主线的多机基础已接近收口 | 按 [多机连接与焦点管理](MULTI_VEHICLE.md) 推进 MV0-MV6：多链路、共享链路解复用、车辆生命周期、active/selected、分机状态隔离、多机 UI、批量动作和签名自动探测 | MV1-MV6 第一版和候选密钥自动探测已完成；剩余风险集中在真实总线验收、异步竞态矩阵、系统 UID 身份策略和复杂任务图层 | 同一链路的 sysid=1/2 数据不串；切换 active 后遥测/任务/参数不残留；跨车辆 ACK 不能误匹配；单机流程不增加步骤；批量动作逐机报告结果；自动探测不泄漏密钥 |
| E. 0.1.0 产品化门槛 | P2；在扩大功能前建立可信基线 | 汇总安全敏感流程验收；检查 ArduPilot/PX4 capability 矩阵；清理稳定 FFI 契约与弃用入口；定义崩溃/日志收集、配置迁移和发布回滚策略 | 由 A-D 和已承诺的 MV 切片真实结果决定范围；不得把未完成的平台、固件或多机能力写成已支持 | 发布清单全部通过或明确列出已知限制；关键错误可诊断；数据/任务文件升级策略有测试；每个平台支持声明与实际验收一致 |

## 建议实施顺序

1. **先做 A 阶段**：这是已有用户流程的可靠性提升，且比新增任务格式或页面更直接影响飞控操作安全。
2. **A 稳定后收口 MV 阶段**：按 [多机连接与焦点管理](MULTI_VEHICLE.md)，MV1-MV6 第一版和签名自动探测已完成；优先处理异步操作超时/取消竞态、真实飞控总线和复杂地图任务图层。
3. **B/C/D 可按资源与 MV 交错**：多机链路改造涉及 Core/FFI，必须单独跑聚焦回归；其他任务文件、诊断和平台工作不能绕过该门禁。
4. **最后定义 0.1.0 范围**：版本号是验收结论，不应预先承诺具体日期或把路线表直接映射成发布承诺。

## MP / QGC / M-GCS 的取舍

| 主题 | MP 侧重 | QGC 侧重 | M-GCS 建议 |
| --- | --- | --- | --- |
| ArduPilot 深度 | 参数、任务和专用调校覆盖广 | 以稳定通用流程和固件插件隔离差异 | 保持 ArduPilot-first，但新增功能通过 firmware profile/capability 表达，避免前端按固件名散落分支 |
| 交互工作流 | 直接、密集，熟练用户效率高 | 状态门控清晰、危险动作确认完整 | 采用 QGC 的状态门控和确认；在参数/诊断深度上逐步吸收 MP 的成熟能力 |
| 任务传输 | 显式 Read/Write，覆盖前提示 | 显式 Download/Upload，脏状态保护 | 已有显式操作基础；补齐进度、取消、失败恢复、回读验证和变更诊断 |
| 架构 | 历史包袱下功能集中、ArduPilot 集成深 | Vehicle/Plugin 分层和跨平台产品化经验 | 不照搬任一方代码；保持 Core/FFI/Flutter 单向边界，协议与领域规则归后端 |
| 近期不追求 | 全量复制 Mission Planner 菜单与参数页 | 一次实现 QGC 全部移动端和高级载荷能力 | 多机按 [实施计划](MULTI_VEHICLE.md) 推进；暂不做蜂群、编队算法、多链路自动主备和完整载荷生态 |

## 暂不纳入近期范围

- **蜂群/编队控制**：多机连接、焦点和逐机命令按 [多机连接与焦点管理](MULTI_VEHICLE.md) 推进；蜂群任务分配和自动协同仍后置。
- **完整固件刷写**：当前刷写实现仍是占位；除非同时具备固件下载、bootloader、断电恢复和实机测试方案，否则不以“打通接口”冒充可用功能。
- **全量参数库复制**：优先补齐实际工作流需要的参数元数据和适用固件标记，不为追求条目数量盲目导入。
- **平台全面支持宣称**：构建成功不代表串口、驱动、生命周期和校准已在该平台通过实机验收。
- **Mission CAD 产品概念**：当前统一使用“任务文档”和“任务规划”；旧 ADR 仅保留历史说明。

## 开发与验收原则

- 每个阶段开始时先用 `docs/CURRENT_STATE.md` 和代码复核基线；路线表不替代事实审计。
- 涉及 Core/FFI 的任务先写清契约、错误语义、测试和兼容策略，再接 Flutter。
- 所有覆盖飞控任务、RTL/Home、校准、参数写入和飞行命令的路径必须保留显式确认，并测试拒绝、超时和断链。
- 默认运行 `tools/preflight.sh`；硬件流程另列手动清单，不把硬件测试伪装成离线 CI 结果。
- UI 延续现有 MiSans、`MgTypography`、`MgColors`、`MgMetrics` 与 macos_ui 组件规范；新增界面前优先验证是否可以复用已有控件。
- 每阶段结束更新 `CHANGELOG.md`、`docs/CURRENT_STATE.md` 及受影响的领域契约；只有发布时才按 `docs/DEVELOPMENT.md` 同步版本号。

# 功能差距分析

当前基线：`0.0.80`

本文用于回答两个问题：

1. M-GCS 当前相对 QGroundControl（QGC）和 Mission Planner（MP）缺少什么？
2. M-GCS 是独立实现、二次开发，还是对上游的复刻？

本文比较的是本地源码快照：

- QGC：commit `bf0096d974dc2792556c61ca783779083d9de41c`，
  `v5.2.0-dev-134-gbf0096d97`
- MP：commit `a2fcd74d64513d0d8fb43fbdd72020fa75aaa974`
- M-GCS：`0.0.80`

## 一、项目定位

M-GCS 是**独立自研、兼容 QGC/MP 工作流的地面站**，不是 QGC/MP 的
源码分支，也不是界面和功能的完整复刻。

判断依据：

- 技术栈不同：M-GCS 使用 `C++17 Core + C FFI + Flutter`；QGC 主体是
  `C++/Qt/QML`；MP 是 `C#/.NET/WinForms`。
- 架构不同：M-GCS 使用自有 `MissionDocument`、`ConnectionManager`、
  `Vehicle` 和 JSON FFI 契约；没有引入 QGC 的 Qt 对象树或 MP 的全局
  `MainV2.comPort` 结构。
- 依赖不同：`third_party/` 当前只包含官方 MAVLink 和 cJSON 等通用依赖。
- 许可证不同：M-GCS 是 MIT；当前 QGC checkout 是 Apache-2.0/GPLv3
  双许可，MP 是 GPLv3。直接复制大段上游源码必须单独做许可证和授权评估。
- 借鉴方式：任务传输、错误语义、任务文件互操作、校准流程等按模块参考
  QGC/MP，但实现落在 M-GCS 自己的边界内。

更准确的产品表述是：

> 面向 ArduPilot 为主、兼容 PX4 的独立地面站；按模块对齐 QGC/MP 的
> 协议事实、状态机、字段和工作流，不复用其 UI 框架或代码分支。

## 二、当前已具备

### 连接与基础飞行

- 串口、TCP、UDP、内存链路、session/vehicle 目标模型。
- heartbeat、断连回收、连接诊断、活动飞控切换。
- 地图、Home、飞机位置、姿态仪、罗盘、遥测仪表条和飞控消息。
- 解锁、上锁、起飞、降落、返航、暂停、改变高度和航向、Go to、
  Orbit、ROI、估计原点等引导动作。
- 长按确认门控统一为 0.5 秒，确认成功后才下发危险命令。

### 任务规划

- `MissionDocument` 编辑、undo/redo、校验、估算和编译。
- SimpleItem、Home、默认高度/速度。
- 从飞控读取、上传、回读核对、清除和脏状态保护。
- `.waypoints`（QGC WPL 110）和 QGC `.plan` 导入导出。
- 固定翼/VTOL 相关任务语义、Home 动态同步区分。
- GeoFence 和 Rally 独立 MAVLink mission type 的编译、上传、下载、
  清除和 verify。
- 参数化 `survey_grid` / `corridor` 后端模型和 QGC ComplexItem 展开。

### 参数、校准与状态

- 参数搜索、分组、描述、类型/范围校验、批量刷新和写入状态。
- ArduPilot 参数重映射、canonical 覆盖率、未分类参数回退。
- 加速度、磁力计、遥控器校准；陀螺仪、气压计和空速后端接口已有。
- 系统状态、传感器健康、端口配置、电机输出、飞行模式、PID 和解锁检查
  的基础页面。
- 统一 FFI 长任务快照和取消入口。

## 三、相对 QGC/MP 的主要缺口

| 领域 | 当前状态 | 主要缺口 |
| --- | --- | --- |
| 固件 | 占位 | 固件发现、下载、bootloader 刷写、断电恢复、版本校验；当前 `mg_firmware_flash` 返回 not supported |
| 飞控配置 | 部分完成 | 机架类型、机型模板、电池、失效保护、ESC、传感器、GPS/罗盘顺序、OSD、降落伞、Remote ID、舵机/继电器完整配置 |
| 校准 | 部分完成 | 加速度/磁力计/遥控器已有；陀螺仪、气压计、空速计完整 UI，传感器方向和容差向导 |

## 四、建议优先级

### P0：安全和单机可用性

1. 固件刷写：实现完整流程，或正式标记为 out of scope。
2. 完整校准和飞控安全配置：机架、传感器、电池、失效保护。
3. 飞行前检查清单和关键遥测缺失提示。

### P1：现场排障

1. Onboard Logs、日志查看器和遥测回放。
2. MAVLink Inspector/Console。
3. 连接质量、丢包、消息速率和参数写入诊断。

### P2：规划与现场任务

1. 围栏/Rally 可视化编辑。
2. Survey/Corridor/Structure Scan/固定翼着陆等 ComplexItem 编辑。
3. 地形剖面、高程冲突和离线地图缓存。
4. KML/SHP/GeoJSON 和测量工具。

### P1.5：多机连接与焦点管理

按 [多机连接与焦点管理](MULTI_VEHICLE.md) 推进：MV1-MV3 链路、车辆选择、
分机状态和精确关闭已完成；MV5 多机地图基础层与 MV6 多选、批量确认、显式目标
分派、逐机结果、候选密钥自动探测、异步超时隔离和围栏/Rally 地图图层已完成。
下一步是系统 UID/固件刷写产品取舍，以及 Survey/Corridor 等复杂项编辑和分层控制。

### P3：载荷与扩展

1. 相机、视频、云台。
2. NTRIP/RTK 和 Follow Me。
3. ADS-B、DroneCAN、脚本和插件。

以上功能不应被机械地“全部照搬”。如果 M-GCS 的目标是面向单机
ArduPilot 现场作业，蜂群、天线跟踪器、传统 OSD、Remote ID 等能力可以
明确保持 out of scope。

## 五、结论

M-GCS 当前是“独立自研 + 上游协议兼容 + 模块级语义借鉴”，不是 QGC/MP
的二次开发分支，也不是完整复刻。它已经形成可用的单机任务、参数、校准、
连接和地图基础，但距离 QGC/MP 的完整生态仍缺少固件配置、日志分析、
复杂任务编辑、地形/离线地图、相机视频和多机扩展等能力。
