# ADR 0005：Mission CAD 由后端领域模型负责

## 状态

提议中。

## 背景

M-GCS 会为不同用户提供不同的界面形态。前端是一个可替换的实现选择，不应成为任务规划能力的所有者。

传统航点列表只保存 MAVLink 任务项，无法表示“该航段为东向 120 米”“该区域按 45 度、30 米间距扫描”这类可继续编辑的设计意图。若由每个前端各自计算几何和生成航点，界面替换会导致后端逻辑重复、结果不一致且难以离线验证。

## 决策

Mission CAD 的源文档、局部坐标、几何实体、约束、编译、校验、估算、诊断和持久化均归属 `core/mission/cad`。

`MissionPlan` 是 Mission CAD 编译后的 MAVLink 目标模型，不是参数化 CAD 文档的源模型。既有任务传输只负责处理编译出的 `MissionPlan`，不参与 CAD 编辑。

`bridge/ffi` 对外提供稳定、版本化、前端无关的 C ABI 与 JSON 契约。任何前端和 CLI 仅作为编辑器或调用方，负责交互和渲染，不得拥有权威几何或飞行任务编译逻辑。

## 影响

正面影响：

- 替换或新增前端时无需重写任务规划后端。
- 任务文件保留参数化设计意图，能够安全地重新编译。
- 几何、约束和飞行限制可以通过离线测试确定性验证。
- 前端能够从同一份编译结果渲染路径、估算和诊断。

成本：

- 需要先建立版本化的文档模型、坐标基准和诊断契约。
- 必须维护 CAD 源实体到生成 MAVLink 任务项的映射。
- 复杂交互在前端可做预览，但提交后仍需要等待后端权威结果。

## 验收条件

1. 纯 C++ 离线测试即可完成 CAD 文档的解析、编辑、编译和校验。
2. 不同前端针对同一份 `.mgcad.json` 和相同 profile 得到等价的编译结果。
3. FFI 头文件、JSON schema 和诊断不包含任何前端框架、widget、页面或地图供应商专有概念。
4. CAD 编译本身不触发飞控写入；上传必须走既有显式任务传输流程。
