# 增添功能

本文是简短的开发参考，不是额外门禁。当前改动以根目录 `AGENTS.md` 为准。

## 先确认边界

1. 找到真实调用方、拥有生命周期的模块和已有测试。
2. 保持依赖方向：`flutter_shell → bridge/ffi → core → third_party`。
3. 前端消费 bridge/FFI 已整理的结果，不在页面里解释协议原始值或固件能力。
4. 有状态逻辑放在实际拥有该状态和生命周期的模块；不要为了“无状态”标签搬运代码。
5. 新抽象必须有当前真实使用方。没有第二个实现或明确测试替身时，不预建工厂、注册表或扩展点。

## 常见改动路径

### 前端功能

页面调用控制器，控制器调用 backend，backend 调用 FFI。新增或修改 FFI 时，先确认现有 backend 是否已经覆盖该契约；不要让页面直接依赖 `dart:ffi` 或原始协议字段。

### Core 功能

把协议解析、状态机和飞控语义放在 `core/`，并让其保持可独立测试。持锁路径不做阻塞 I/O，也不调用外部回调。

### 异步飞行操作

操作必须绑定明确的车辆和会话。完成、拒绝、超时、取消都要传回调用方；“已经发送”不能当作“已经成功”。检查连接切换、重连、销毁和重复调用路径。

### 多固件或平台差异

当前没有真实需求时，不预建 PX4 工厂或通用平台抽象。出现真实差异时，先在当前调用链中做最小实现，并用测试固定行为；只有长期架构确实改变时才创建 ADR。

## 完成前检查

- 相关调用方和生命周期清楚；
- 没有引入反向依赖、无使用方抽象或锁内 I/O；
- 错误、拒绝、超时、取消没有被转换成成功；
- 有能够复现新行为或 bug 的相关测试；
- 运行与改动直接相关的检查，并在说明中列出未运行的验证。

不要求为普通功能新增文档、对照表、偏差编号或 ADR。
