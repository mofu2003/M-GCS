# 维护

本文只保留当前项目真正需要的维护基线。现行硬约束以根目录 `AGENTS.md` 为准。

## 处理顺序

1. 先确认问题有复现路径、实际后果和明确归属。
2. 做最小修复，尽量不改变无关接口和行为。
3. 为修复增加回归测试，或说明为什么已有测试足够。
4. 运行与改动直接相关的检查；发布前可运行 `tools/preflight.sh`。

## 代码质量

不要按文件行数、类数量或固定周期自动拆分。代码变复杂时，沿真实调用链判断职责、生命周期和测试边界；只有拆分能降低当前复杂度并有真实使用方时才抽象。

重点保持：

- `flutter_shell → bridge/ffi → core → third_party` 的依赖方向；
- core 不依赖上层，持锁路径不阻塞、不回调外部代码；
- 异步操作绑定车辆和会话；
- 飞控拒绝、超时、取消不会被伪装成成功；
- 第三方源码和本地生成物不进入提交。

## 文档维护

普通 bug 修复和功能改动不要求同步更新历史约束、parity、known deviations 或新增 ADR。只有长期改变公开 ABI、线程模型、许可边界或飞行安全语义时，才补充对应 ADR 或事实记录。

历史文档中的旧数字、旧阶段和旧规则不作为当前状态；当前状态以代码、测试和本次验证结果为准。
