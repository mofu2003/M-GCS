## 2. 分层依赖：存在一处逆向依赖

文档声明的依赖方向是单向的：

```text
flutter_shell/  →  bridge/ffi/  →  core/  →  third_party/
```

### 2.1 实测发现

`core/include/core/vehicle/vehicle.h:17` 有一行 `#include "telemetry_cache.h"`，
该头文件实际位于 `bridge/ffi/telemetry_cache.h`；`Vehicle` 的成员之一即
`mg::bridge::TelemetryCache cache_`（`vehicle.h:149`）。

**根因**：根 `CMakeLists.txt:226-229` 把 `bridge/ffi` 挂到了 `mgcore` 目标的
**PUBLIC** include 路径上，于是 `core/` 可以用裸文件名 include `bridge/ffi` 的头。

### 2.2 为什么此前没被发现

- 之前"core 对 bridge/ffi 引用为 0"的结论，是用 `bridge/` 前缀做文本匹配得出的。
  裸文件名的 `#include` 不匹配该前缀，因此漏检。
- `core/tests/test_bridge_architecture_guards.cc` 的 12 个断言只检查 bridge 层自身的
  文件规模与分组收敛（grab-bag 体积、领域拆分等），**不校验 core→bridge 方向**，
  所以门禁也抓不到。

### 2.3 修法（二选一，均属公共接口变更，改前需先通知）

1. 把 `TelemetryCache` 下沉到 `core/`，让 `bridge/ffi` 改为使用它；或
2. 把 `bridge/ffi` 从 `mgcore` 的 PUBLIC include 路径改为 PRIVATE，并让 `Vehicle` 依赖
   一个 core 侧定义的接口。

无论哪种，都应同步给 `test_bridge_architecture_guards.cc` 补一条方向断言，
否则同类问题会再次漏检。

## 3. FFI 契约面的消费情况

契约面共 **266 个 `mg_*` 导出**（12 个领域头），前端实际调用 **30 个**。
口径：Dart 侧 `lookup('mg_*')` 的字面量，不用全文匹配（否则会把 `MgColors`、
`MgAnimatedNumber` 这类 Dart 类名算进来）。

按"谁在用"三分，比"11%"这个单一数字更能说明问题：

| 归处 | 数量 | 占比 |
| --- | --- | --- |
| 前端在用 | 30 | 11% |
| 有测试覆盖，但前端未接 | 131 | 49% |
| 既无前端调用、也无测试触达 | 105 | 39% |

按领域头拆分（导出数 / 前端在用 / 仅测试 / 两者皆无）：

| 领域头 | 导出 | 前端在用 | 仅测试 | 两者皆无 |
| --- | --- | --- | --- | --- |
| telemetry | 46 | 7 | 33 | 6 |
| configuration | 43 | 5 | 19 | 19 |
| flight | 32 | 0 | 24 | 8 |
| mission | 25 | 0 | 9 | 16 |
| logging | 22 | 0 | 2 | 20 |
| connection | 21 | 6 | 10 | 5 |
| params | 20 | 6 | 3 | 11 |
| payload | 17 | 0 | 13 | 4 |
| geofence | 16 | 0 | 4 | 12 |
| core | 12 | 3 | 8 | 1 |
| firmware | 7 | 3 | 3 | 1 |
| environment | 5 | 0 | 3 | 2 |

### 3.1 这不是缺陷，是既定策略

`API_CATALOG.md` 明写了稳定性三档，其中：

> **Specialized**: public, but intended for a feature-specific client rather than a
> general-purpose client. Its lack of a first-party binding does not make it removable.

并进一步说明：mission、flight command、geofence、payload、logging、SITL、firmware 属于
"尚未接入所有客户端工作流"的专用公开面。也就是说契约面本就按"给外部/专用客户端"设计，
**不是按当前 UI 裁剪的**，不应以"前端没用"为由删除。

### 3.2 但有三条真问题

**(a) 前端写参数走的是一个没进 catalog 的入口 —— 违反铁律三**

前端用的是 `mg_config_read_param` / `mg_config_write_param`（声明在
`bridge/ffi/ffi_api_params.h:26-27`，实现在 `ffi_config_extra.cc`），
连同 `mg_config_write_params` 在内，**这三个函数在 `API_CATALOG.md` 里一次都没出现**。
而 catalog 的 Preferred 参数写入入口写的是 `mg_params_set`。

`AGENTS.md` 铁律三要求契约变更必须同步"声明 + 实现 + 测试 + `API_CATALOG.md` + 文档"，
缺一项即违规。这属于既成欠账。

**(b) 前端跳过了所有聚合接口**

`ffi_diagnostics.cc` 实现了 5 个聚合入口，前端一个都没接：

| 未接入的聚合接口 | 前端实际用的替代 |
| --- | --- |
| `mg_connection_get_diagnostics` | `mg_connection_get_session_state` |
| `mg_telemetry_get_dashboard_snapshot` / `mg_system_get_diagnostics` | `mg_telemetry_get_freshness` + `mg_vehicle_get_session_status` |
| `mg_operations_get_snapshot` / `mg_operations_cancel` | **无** |

后果是具体的：参数同步与任务传输这类长任务，UI 中**没有取消入口**，进度也是自行拼接而非走统一视图。
`ARCHITECTURE.md` 写明这些接口的设计目的正是"让调用方不自行拼接多个底层快照"——前端目前在做它想避免的那件事。

**(c) 前端在用的 30 个里，有 5 个没有测试覆盖**

`mg_calibration_cancel`、`mg_params_get_by_name`、`mg_serial_get_uart_names`、
`mg_stream_set_interval`、`mg_vehicle_request_firmware_version`。

这 5 个是"线上在用、回归没兜住"的组合，比 105 个无人区更该优先补测试——
它们是唯一被真实用户路径触达却无网的。

### 3.3 契约面没有在收缩

- `bridge/ffi` 全文 **deprecated 标记 0 个**。
- v0.0.6 / v0.0.7 / v0.0.8 三个 tag 的导出数**均为 266**，一个不增一个不减。

catalog 写了"Mark replacements as compatibility before removal"的退役流程，
但 `mg_param_list` / `mg_cmd_*` / `mg_cal_*` / `mg_fence_*` 这些兼容入口既没标 deprecated、
数量也没变过。退役机制目前没有运转，契约面只会因"不可按当前消费情况删除"而持续堆积。

- 全部 105 个**都有真实实现**。只有 2 个是空壳：`mg_rc_calibrate_save`（直接 `return ok()`，

  真正未实现的 `mg_firmware_flash` 不在此集合内。
- **11 个是兼容别名**，纯转发，本身零逻辑成本。
- **8 个是安全敏感的飞行指令**，是无人区中最该先补测试的一类。

## 6. 建议的处置顺序

按"风险 / 成本"排序，前两项是纯补账，不改行为：

1. **把 `mg_config_*` 三个函数补进 `API_CATALOG.md`**，并明确它们与 `mg_params_set` 的关系。
   这是铁律三的既成欠账，成本最低。
2. **给 5 个"前端在用但无测试"的函数补契约测试**（见 3.2c）。它们是唯一被真实路径触达却无网的。
3. **统一参数写入入口**：前端切到 `mg_params_set`，或反过来把 catalog 的 Preferred 改成现状。
   两者取其一 —— 这是安全敏感路径，改前需明确决定。
4. **把 `mg_operations_*` 接进 UI**，给长任务一个取消入口。
5. **给 8 个飞行指令补测试**（`mg_command_*` 四个 + 高度/半径四个），它们在
   `ARCHITECTURE.md` 的高风险路径清单里。
6. **给 `mg_params_prepare_change_set` / `_commit_change_set` 补验证**。
   整套"`_ENABLE` 最后写入"的排序语义目前既无前端也无测试覆盖，是写参数路径中最易出事的地方。
7. **标记第一批 deprecated**：11 个已登记兼容别名 + `mg_rc_calibrate_save`（空实现）
   + `mg_log_list`（返回空列表），让退役机制开始运转。

**不建议**按"前端没用"为由删除 mission / geofence / logging / params 的大头 ——
这些后端逻辑完整（任务导入导出、围栏 KML 导出、FTP 文件传输），只是没有对应 UI 页面，
属于产品路线问题，不是工程债。

# 前端实际调用面统计
