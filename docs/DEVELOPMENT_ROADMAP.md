# M-GCS 后续发展计划

> 状态：建议路线，尚非版本承诺。当前代码基线：`0.0.62`。
> 本计划用于确定开发顺序和验收条件；具体版本归属应在每个阶段开始前，根据代码状态与用户优先级确认。

“什么时候可以停”的判定口径见 [完成定义与后端维护收口](DEFINITION_OF_DONE.md)：
后端维护循环的退出条件（复杂任务可编译、围栏/Rally 闭环、参数阈值、未做项收口）
已在其中显式列出。

## 方向摘要

M-GCS 当前已有任务文档编辑、后端校验/编译、任务上传/下载/验证、`.waypoints` / QGC
`.plan` SimpleItem 互操作、地图 Home/飞机位置和基本引导操作。近期不应继续堆叠零散
页面，而应优先把已有安全敏感工作流做成可靠闭环，再扩展复杂格式和领域覆盖，随后
补足运维诊断与平台实机验证。

目标不是逐项复制 Mission Planner（MP）或 QGroundControl（QGC），而是按模块选择
质量更高的实现：任务模型、链路生命周期、跨平台结构和测试治理优先参考 QGC；
ArduPilot 专用命令、参数、校准、固件和飞行行为优先参考 MP。组合时明确边界，
协议语义、任务编译和校验仍集中在 M-GCS 后端。默认归属见
[MP / QGC 上游实现择优准则](UPSTREAM_CODE_SELECTION.md)。

## 本轮维护决策

M-GCS 不选择“全盘 MP”或“全盘 QGC”，而采用明确的组合边界：

```text
官方 MAVLink / 飞控协议事实
              ↓
QGC：框架、生命周期、状态机、取消、跨平台和测试治理
              +
MP：ArduPilot 参数、校准、模式、任务字段和现场兼容
              ↓
M-GCS Core -> FFI -> Flutter
```

维护顺序固定为：

1. 先修复安全敏感流程的状态、错误和恢复语义。
2. 再拆分内部大文件，保持公开 FFI 和用户行为不变。
3. 再补任务、参数、围栏/Rally 和平台能力。
4. 最后才扩大 UI 和产品功能范围。

本轮不做框架替换，也不复制 QGC 的 Qt/QML 或 MP 的 WinForms 结构。

## 当前基线与差距

| 领域 | M-GCS 当前基线 | MP / QGC 可借鉴点 | 当前主要差距 |
| --- | --- | --- | --- |
| 任务规划 | 任务文档、命令目录、测绘实体、校验/编译、上传/下载/验证、operations 进度与取消、回读核对、脏状态、拖拽排序；Flutter 地图规划面板 | 两者均采用显式 Read/Write 或 Download/Upload；覆盖本地未保存内容前先确认 | 复杂 QGC 任务项、GeoFence/Rally 和更细的跨固件错误语义仍未补齐 |
| 地图与飞行操作 | Home/飞机标记、地图偏好保存、引导操作及确认 | QGC 按飞行状态、机型和 capability 控制动作可用性；关键操作前确认 | 继续核对定位有效性、能力差异和异常状态呈现；避免对不支持动作显示可执行入口 |
| 任务格式与相关领域 | `.waypoints` 互操作；QGC `.plan` SimpleItem、ComplexItem、GeoFence、Rally 已纳入文档模型并往返无损；ComplexItem 复用 QGC 已算好的任务项参与编译/上传；围栏和 Rally 几何已校验，并可各自按 QGC 编码编译/上传/清除/回读与 verify | QGC `.plan` 将任务及相关规划信息组织为可保存文件；MP 有成熟 ArduPilot 任务与参数流程 | ComplexItem 内部字段仍只读（几何来自 QGC，不可在 M-GCS 编辑）；围栏/Rally/ComplexItem 统一编辑工作流仍缺 |
| 诊断与长操作 | 有连接/系统/遥测诊断及 operation 后端 API | QGC 将连接、车辆状态、命令结果和进度反馈串成连续工作流；MP 提供面向 ArduPilot 的丰富检查 | Flutter 尚未完整使用聚合诊断和长任务取消/统一进度；不同页面状态体验不一致 |
| 平台质量 | macOS 主开发路径；Windows/Linux 构建路径存在；Android USB Host 基础工程存在 | MP 覆盖 Windows 为主的 ArduPilot 场景；QGC 重点支持桌面和移动平台 | Windows 尚缺系统化真机验收；Linux/Android 串口和关键工作流需明确支持级别并验证 |

## 阶段计划表

阶段不绑定日期，也不自动等同于一个发布版本。优先按表中顺序推进；若用户改变重点，应先重排阶段，再开始涉及 FFI 或安全行为的工作。

| 阶段 | 优先级 / 目标 | 主要工作 | 依赖与风险 | 完成标准 |
| --- | --- | --- | --- | --- |
| A. 任务闭环可靠性 | P0；让现有规划功能可预期、可恢复 | 统一任务上传/下载进度、成功/失败/超时和取消入口；本地文档脏状态及覆盖确认；上传完成后显式回读并展示验证结果；校验错误定位到对应实体/参数；航点与地图双向选中、列表重排 | 先复核现有 `mg_mission_get_progress`、operation API 和页面状态，优先复用；若需改 FFI，必须同步实现、测试、API Catalog、文档和绑定；取消传输需明确协议终止语义 | 离线/模拟测试覆盖成功、拒绝、超时、断链、取消及重试；模拟“本地未保存任务被下载覆盖”必须先确认；回读验证能区分通过与差异；列表重排后地图序号和编译顺序一致 |
| B. 任务文件与领域互操作 | P1；提高任务可交换性，不破坏现有任务契约 | 设计 QGC `.plan` 导入/导出映射；对 unsupported 字段给出诊断而非静默丢弃；评估围栏与 Rally 纳入统一文件/任务文档的边界；补齐几何校验、版本化和往返测试 | 先定义可逆/不可逆字段映射；Survey/Corridor 导出到普通航点会丢失设计意图；Fence/Rally 涉及不同 MAVLink mission type 和飞控支持差异 | 有格式规范与字段映射表；有效样例 round-trip 测试通过；未知字段/不支持命令有明确告警；不会静默改变飞控任务；围栏/Rally 独立类型和能力差异有测试 |
| C. 诊断与运维工作流 | P1；缩短连接、任务、参数和校准问题的定位时间 | Flutter 接入聚合诊断快照；统一长任务进度、取消和终态；连接质量/遥测 freshness 可见；参数变更结果可追踪；校准历史和飞行日志入口按现有后端能力梳理 | 依赖 FFI 生命周期和事件线程安全；诊断字段需有稳定语义；不新增只展示却无可操作价值的卡片 | 模拟断连、超时、拒绝和重连时状态无歧义；页面隐藏时停止轮询；进度与后端状态一致；取消后资源释放且可重新开始 |
| D. 跨平台实机稳定性 | P1；将“有构建路径”推进到“关键流程可验收” | Windows：串口连接/断连、遥测、参数读写、校准、任务上传下载；Linux：原生构建和串口基本流程；Android：先明确支持范围，再验证 USB-serial 权限、设备拔插和生命周期 | 需要对应平台设备、飞控和安全测试条件；飞控串口是排他资源；Android 驱动差异大，不宜承诺通用支持前提 | 每个平台有版本化验收清单、驱动/设备记录和结果；无硬件的场景由 simulation 覆盖；明确标注已验证、未验证和不支持项 |
| E. 0.1.0 产品化门槛 | P2；在扩大功能前建立可信基线 | 汇总安全敏感流程验收；检查 ArduPilot/PX4 capability 矩阵；清理稳定 FFI 契约与弃用入口；定义崩溃/日志收集、配置迁移和发布回滚策略 | 由 A-D 的真实结果决定范围；不得把未完成的平台或固件支持写成已支持 | 发布清单全部通过或明确列出已知限制；关键错误可诊断；数据/任务文件升级策略有测试；每个平台支持声明与实际验收一致 |

## 建议实施顺序

1. **先做 A 阶段**：这是已有用户流程的可靠性提升，且比新增任务格式或页面更直接影响飞控操作安全。
2. **A 阶段稳定后做 B 阶段最小闭环**：先完成 QGC `.plan` 字段映射和导入/导出测试，再决定围栏/Rally 是否共享文件容器；不要一次扩成全功能规划套件。
3. **C 与 D 可以按资源交错**：运维诊断是跨平台共用能力；Windows 真机验收可在对应后端/桥接稳定后并行推进，但同一飞控不可并发测试。
4. **最后定义 0.1.0 范围**：版本号是验收结论，不应预先承诺具体日期或把路线表直接映射成发布承诺。

## MP / QGC / M-GCS 的取舍

| 主题 | MP 侧重 | QGC 侧重 | M-GCS 建议 |
| --- | --- | --- | --- |
| ArduPilot 深度 | 参数、任务和专用调校覆盖广 | 以稳定通用流程和固件插件隔离差异 | 保持 ArduPilot-first，但新增功能通过 firmware profile/capability 表达，避免前端按固件名散落分支 |
| 交互工作流 | 直接、密集，熟练用户效率高 | 状态门控清晰、危险动作确认完整 | 采用 QGC 的状态门控和确认；在参数/诊断深度上逐步吸收 MP 的成熟能力 |
| 任务传输 | 显式 Read/Write，覆盖前提示 | 显式 Download/Upload，脏状态保护 | 已有显式操作基础；补齐进度、取消、失败恢复、回读验证和变更诊断 |
| 架构 | 历史包袱下功能集中、ArduPilot 集成深 | Vehicle/Plugin 分层和跨平台产品化经验 | 不照搬任一方代码；保持 Core/FFI/Flutter 单向边界，协议与领域规则归后端 |
| 近期不追求 | 全量复制 Mission Planner 菜单与参数页 | 一次实现 QGC 全部移动端、多机和高级载荷能力 | 暂不做蜂群、多链路控制和完整载荷生态；先让单机关键流程稳定、可验证 |

## 暂不纳入近期范围

- **多机/蜂群控制**：先把单飞控 session、焦点切换和安全命令目标彻底验证，再评估多机操作模型。
- **完整固件刷写**：当前刷写实现仍是占位；除非同时具备固件下载、bootloader、断电恢复和实机测试方案，否则不以“打通接口”冒充可用功能。
- **全量参数库复制**：优先补齐实际工作流需要的参数元数据和适用固件标记，不为追求条目数量盲目导入。
- **平台全面支持宣称**：构建成功不代表串口、驱动、生命周期和校准已在该平台通过实机验收。
- **Mission CAD 产品概念**：当前统一使用“任务文档”和“任务规划”；旧 ADR 仅保留历史说明。

## 开发与验收原则

- 每个阶段开始时先用 `docs/STATUS_AUDIT.md` 和代码复核基线；路线表不替代事实审计。
- 涉及 Core/FFI 的任务先写清契约、错误语义、测试和兼容策略，再接 Flutter。
- 所有覆盖飞控任务、RTL/Home、校准、参数写入和飞行命令的路径必须保留显式确认，并测试拒绝、超时和断链。
- 默认运行 `tools/preflight.sh`；硬件流程另列手动清单，不把硬件测试伪装成离线 CI 结果。
- UI 延续现有 MiSans、`MgTypography`、`MgColors`、`MgMetrics` 与 macos_ui 组件规范；新增界面前优先验证是否可以复用已有控件。
- 每阶段结束更新 `CHANGELOG.md`、`docs/STATUS_AUDIT.md` 及受影响的领域契约；只有发布时才按 `docs/DEVELOPMENT.md` 同步版本号。
