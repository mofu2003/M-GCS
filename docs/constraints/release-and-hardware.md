# 发布与硬件

本文件的规则都是约束（MUST）。每条写明违反后果和验证方式。

**R1 版本号一致**
以下四处必须一致：`CMakeLists.txt` 的 `project(... VERSION)`、`flutter_shell/pubspec.yaml` 的 `version`、`bridge/ffi/ffi_api_core.h` 的 `MGCORE_VERSION_*`、`CHANGELOG.md` 的最新发布条目（不含 Unreleased）。
- 违反后果：发布的版本信息错误，用户无法判断自己使用的版本。
- 验证：`tools/preflight.sh` 校验四处；`tools/release.sh` 在编辑前检查必需文件，并同步 README 中的版本。

**R2 发布顺序**
改版本号，更新 CHANGELOG，本地提交，本地打标签。用户明确要求时才推送。
- 违反后果：标签与内容不一致。
- 验证：评审时检查。

**R3 远端操作需用户指示**
推送、创建或删除远端分支、推送标签、强制推送，只在用户明确要求时执行。
- 违反后果：未经审阅的改动被发布出去。
- 验证：操作约定加评审。

**R4 飞控串口独占**
飞控串口同一时间只能被一个进程占用。硬件相关操作前，必须确认没有其他会话正在使用该串口。
- 违反后果：串口冲突，或误操作飞控。
- 验证：测试前检查端口占用情况。

**R5 硬件测试有人在场**
硬件测试必须有人在场，并在执行前确认机体安全（拆桨、未解锁）。
- 违反后果：机体意外动作。
- 验证：每次执行前的检查清单。

**R6 LGPL FFmpeg 合规**
构建本地视频解码时，FFmpeg 必须使用 LGPL 构建（不得启用 `--enable-gpl`），并动态链接（见 `docs/adr/0008-video-decode-backend.md`）。发布含 FFmpeg 的构建时，随包附 LGPL 许可文本与对应 FFmpeg 源码获取方式（或书面提供），并在 SBOM/第三方依赖清单登记版本。
- 违反后果：GPL 传染导致发布物许可不合规。
- 验证：构建脚本检查 FFmpeg `--disable-gpl`；发布检查表核对许可与源码获取方式；`tools/preflight.sh` 不自动覆盖此项，需人工确认。
